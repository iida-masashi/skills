# Solution Market Research

## Overview

特定の業務機能（WMS、TMS、ERP、CRM等）向けのソフトウェア/システムソリューションを業界横断で調査し、RFP作成・ベンダー候補選定に使えるVault資料として整理する汎用ワークフロー。食品・お菓子業界向けWMS/TMS調査（`D:\Vault\wmstms`）で確立した型を抽象化したもの。

**核心原則**:
1. Geminiや他AIが生成した既存調査資料は、製品名・会社名・数値の**存在そのもの**を疑ってかかる。ハルシネーションで実在しない製品名が混ざることがある。
2. 一次資料（ベンダー公式サイト・プレスリリース・IR）でしか主張を確定しない。裏付けが取れない項目は正直に「?」「未確認」「非公開」と明記し、楽観補完しない。
3. Vault本体には**現在の事実だけ**を書く。検証の経緯・訂正プロセス・「1回目の調査では誤っていたが」といった記述は本文に残さず、専用の履歴ログファイルに集約する。
4. 比較表・適合度マトリクスは、ユーザーの意思決定（RFP発行、候補選定）に直結する成果物として扱い、列の追加・削除はユーザー指示に忠実に従う。

## When to Use

- 特定機能領域（WMS/TMS/ERP/MES/CRM等）向けの製品・ベンダーを新規に調査し、比較表を作る
- AIが作成した既存の調査資料を裏取りする（「Geminiが作った資料なので信用していない」等）
- 既存資料の中に実在しない製品名・会社名（ハルシネーション）が混ざっていないか確認する
- 各ベンダーの導入企業数・市場シェア・業界内シェアを調べる
- RFP用のFit/Gap適合度マトリクス（機能要件×ベンダー）を作成・更新する
- 機能要件一覧（チェックリスト）そのものの過不足を検証する

**使わない場面**: 単発で1製品の概要だけ知りたい（WebSearch/WebFetchで十分）。特定1社の詳細なIT導入事例を深掘りしたい（`value-chain-research`の企業ケーススタディ軸の方が近い）。業界のSCM組織構造・バリューチェーンそのものを調べたい（`value-chain-research`を使う）。

## How to Run

### フェーズ0: 既存資料の信頼性チェック（AIが作った資料がある場合）

既存資料がある場合、着手前に「存在そのものが怪しい製品・会社はないか」を明示的に洗い出す。個別の数値誤りより先に、この存在確認を行う——後から実在しない製品を軸に比較表を作り込むと手戻りが大きい。

各製品名・会社名について`web-search`スキルで単独検索し、公式サイトが実在するか確認する。特に注意すべきハルシネーションのパターン：
- 社名と製品名の混同・合成（例:「シーネット」社の実際の製品名は「ci.Himalayas」なのに「ci-nect」という存在しない名前を生成）
- 別会社の製品を混同（例: 名前が似た無関係の別会社）
- カテゴリの取り違え（該当機能のツールではなく、隣接カテゴリのツールを誤って分類）

### フェーズ1: スコープ確認

ユーザーに対象機能領域・対象業界（あれば業界特有要件）・想定用途（RFP作成か、単純比較か）を確認する。

### フェーズ2: 機能要件の妥当性確認

比較表を作る前に「そもそもこの機能領域に必要な要件一覧は正しいか」を確認する。業界特有の要件（食品なら賞味期限管理・アレルゲン対応、医療なら規制トレーサビリティ等）が抜けていないか、汎用要件と業界特有要件を分けてチェックリスト化する。

### フェーズ3: ソリューション調査・裏取り

`web-search`スキル（`gemini_websearch.py` / `gemini_webfetch.py`）で各ソリューションを調査する。

| 項目 | 調査方法 |
|---|---|
| 製品の実在性 | 公式サイト・製品ページの直接確認 |
| 導入企業数・シェア | 業界メディアの調査記事、ベンダー公式発表数値。`--check`で個別URL裏付け |
| 特定業界での導入事例 | ベンダー公式の導入事例ページ、プレスリリース |
| 機能適合度 | 製品公式の機能ページ・マニュアル・導入資料 |

**数値の信頼度に注意**: GeminiのようなAI要約は複数ソースを合成した曖昧な集約値（「累計1,000事業所」等）を出すことがある。`--check`フラグで個別URLを直接検証し、ページ内に直接記載がなければ「不明」「要再確認」と明記する。裏付けの強さ（プレスリリース本文で直接確認 vs AI要約のみ）を区別して記載する。

再検証は「疑わしい1点」だけで終わらせず、同じ調査プロセスの他の箇所（マテハン連携、多言語対応等の横断的な機能軸）にも同種の見落としがないか横展開する。

### フェーズ4: Vault構造化

以下のファイル分割を出発点として使う（対象領域・規模に応じて調整）:

```
00_INDEX.md                          全体インデックス（ファイル一覧・Mermaid俯瞰図）
01_業界特有課題と機能要件.md          業界特有の課題・要件の整理
02_主要ソリューション比較_A領域.md     機能領域A（例: WMS）のベンダー比較表
03_主要ソリューション比較_B領域.md     機能領域B（例: TMS）のベンダー比較表
04_機能要件一覧.md                   RFP評価軸となるチェックリスト（必須度付き）
05...                                グローバルメガベンダー等の個別深掘り調査
0N_RFPテンプレート.md                RFP章構成・記載要件ガイド
0N_適合度マトリクス.md                機能要件×ベンダーのFit/Gap（◎○△×）比較
0N_調査履歴・訂正ログ.md              検証経緯・訂正の記録（本体には書かない全て）
```

比較表の列は最低限「ソリューション名／提供ベンダー／タイプ（クラウド/オンプレ等）／対象業界での強み・特長」を持つ。ユーザー指示に応じて「導入企業数」「主な導入企業（対象業界関連）」「特有機能対応の有無」等を追加する。列が増えすぎたら可読性とのトレードオフをユーザーに明示してよいが、明示的な追加指示は優先する。

### フェーズ5: 履歴ログ運用

`調査履歴・訂正ログ.md`に日付見出しで追記していく。含めるもの:
- 何を検証したか（背景）
- 検証結果（誤り発見・訂正・新規判明事実）
- 検証方法（使ったツール・URL）

本体資料（比較表・マトリクス等）には**現在の事実のみ**を残す。以下は本体から除去し、履歴ログへ移す:
- 「1回目の検証結果（誤り）」「再検証の結果、〜と判明した」等の経緯語彙
- 「◯◯という名称は存在せず、△△との混同・誤記」等の訂正過程の説明（正しい名称だけを本体に残せばよい）
- 「上位2社は既存候補、3位は新規追加」等、資料がどう変化したかの自己言及

判断基準: 過去形（〜が判明した／〜を訂正した／〜が誤りと分かった）で書かれた文は本体から除去。現在形（〜は未確認／〜は非公開）で書かれた文は残してよい。

## Key Practices (learned the hard way)

- **存在確認は個別数値の裏取りより優先度が高い**。実在しない製品を軸に比較表・マトリクスを作り込んでから発覚すると手戻りが大きい。着手直後にフェーズ0を必ず通す。
- **初回調査は「トップページ・概要ページのみ」で終わりがちで、個別サービスページまで見ていないと誤った結論(「自社開発なし」等)に至る**。「存在しない」と結論する前に、製品ページ・サービス一覧ページまで踏み込む。
- **横断的な機能軸（多言語対応、マテハン連携、モバイル/タブレット対応等）は初回調査で見落とされやすい**。1件の再検証指示をきっかけに、同種の軸を全ベンダーに対して横展開して確認する。
- **市場シェア調査は機能領域によってデータの粒度が異なる**（例: WMS市場には明確な統一シェア調査があったが、TMS市場は調査区分が異なる複数データしかなかった）。無理に単一の数値に統合せず、出典ごとの調査条件（時期・対象範囲・回答者数）を明記して併記する。
- **AI要約の集約値は`--check`で個別URL検証すると「不明」と出ることがある**。それでも数値自体を消さず、「Gemini要約由来・個別ページでの直接裏付けは取れず」と信頼度を区別して記載すれば資料として有用。
- **経緯記述の混入はユーザー指摘後も繰り返し起きる**。1回「経緯は履歴ログへ」と指示されても、その後の編集で新たに経緯語彙が混入することがあるため、本体を編集するたびに過去形の文がないか確認する。
- **ランキング・認定年数等の「年次・版」はWebSearch要約で取り違えられやすい**。例：Kantar BrandZの「Pampers 100位・$17bn」という数値がWebSearch要約では「2026年版」として提示されたが、公式ページを直接WebFetchすると実際は「2023年版」の記載だった。年次が意味を持つ数値は、要約だけで採用せず一次情報ページで実際の年度ラベルを確認する。
- **一次資料が403・認証壁で直接確認できない場合、複数年にわたる業界メディア報道の一貫性で確度を判断してよい**。例：Gartner Supply Chain Top 25の連続選出年数（Gartner公式プレスリリース本文はアクセス制限）は、2023年「9年連続」→2025年「11年連続」→2026年「12年連続」と、異なる年の複数の業界メディア記事が一貫して増加する数字を報じていたことから、単発の推定ではなく裏付けありと判断した。ただし本文には「業界メディア経由の裏付けであり公式一次資料は直接確認できず」と正直に明記する。
- **WebFetchで取得できない大きめのPDF一次資料（IR資料・統合報告書等）は、Readツールでファイルを直接開くと読める**ことがある。`pages`パラメータは省略する（指定するとpdftoppm未インストール環境で失敗することがある）。8.5MB・77ページのPDFでも`pages`省略で全文抽出に成功した実績あり。

## Common Mistakes

| 症状 | 原因 | 対処 |
|---|---|---|
| 実在しない製品名を軸に比較表を作ってしまう | AI生成資料の製品名を無検証で転記 | フェーズ0で全製品名を個別に実在確認してから比較表作成に入る |
| 「導入企業数が確認できない」と誤って結論 | トップページ・概要ページしか見ていない | 個別サービスページ・導入事例ページまで確認する |
| 本体資料に「訂正しました」「再検証の結果」等の記述が残る | 検証直後にその場で本体へ書き込み、経緯もそのまま残す | 本体は現在の事実のみに統一し、経緯は都度、履歴ログ側へ切り出す |
| 市場シェアを無理に1つの数値に統合 | 出典ごとの調査条件（対象範囲・時期）の違いを無視 | 出典ごとに調査条件を明記して併記する。統一データがない旨も正直に書く |
| 横断的な機能軸の対応漏れが一部ベンダーだけ発覚 | 1ベンダーの再検証で終わり、他ベンダーへの横展開をしなかった | 1件の見落としが見つかったら、同じ機能軸を全ベンダーに対して確認し直す |
| ランキング・認定年数の数値が実際と異なる年度のものだった | WebSearch要約が複数年混在ページから年度ラベルを取り違えた | 年次が意味を持つ数値は一次情報ページを直接WebFetchし、実際の年度表記を確認してから採用する |
