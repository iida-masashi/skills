# Context Compression Skill (rtk-ai philosophy)

このスキルは、LLMエージェントのコンテキストウィンドウをクリーンに保ち、トークン消費を劇的に削減するための「出力事前フィルタリング」ワークフローを規定する。
エージェントはファイル操作やコマンド実行の際、生の出力をそのままコンテキストに流し込んではならない。必ず以下の手法を用いて情報を高密度化（圧縮）すること。

## ツール語彙の対応表

本文は実行環境に依存しない汎用語彙で書く。実際のツール名は環境ごとに読み替えること。

| 汎用概念（本文の表記） | Gemini CLI | Claude Code |
|---|---|---|
| 検索ツール | `grep_search` | `Grep`（`output_mode`, `-C` context, `head_limit`） |
| 部分読み込み | `read_file` の `start_line` / `end_line` | `Read` の `offset` / `limit` |
| ファイル一覧 | `glob` / `list_directory` | `Glob` |
| 末尾抽出 | `Select-Object -Last 30`（PowerShell） | `tail -30`（Bash ツール） |

## 1. コマンド実行時の静音化（Silent Execution）

コマンドを実行する際は、プログレスバーや冗長な情報ログを徹底的に排除せよ。結果（成功・失敗）だけが分かれば良い。
*   **パッケージ管理**: `npm install --quiet --no-progress`, `uv pip install -q`
*   **Git操作**: `git status -s`, `git log --oneline -n 5`
*   **テスト実行**: pytestなら `--tb=short` や `-q` を活用。

## 2. エラーログの蒸留（Log Distillation）

数百行のスタックトレースを丸呑みするのは厳禁。本当に必要な末尾の例外メッセージと、自分のコード上の発生箇所のみを抽出せよ。
*   **末尾抽出**: 出力をパイプして末尾30行程度に絞る（対応表「末尾抽出」参照）。
*   **エラー周辺の抽出**: エラーが予想される場合は、出力をファイルにリダイレクトし、検索ツールで `Exception` や `Error` の周辺（context）だけを検索・抽出する。

## 3. ファイル構造の「目次」抽出（AST/Signature Extraction）

巨大なファイルをいきなり全行読み込むのは無能の極みである。まず構造を把握せよ。
*   **クラス/関数の抽出**: 検索ツールを使い、`def ` や `class ` などのシグネチャのみを検索して、ファイルの骨組み（AST的構造）を把握する。
*   **ピンポイント読み込み**: 骨組みから対象の行番号を特定し、部分読み込み（開始行＋行数の指定）で必要な箇所だけを外科的に抽出する。

## 4. 差分（Diff）ベースの観測

ディレクトリ内の全ファイルリストや、ファイル全体の再読み込みを安易に行わない。
*   状態確認は `git diff` や `git diff --name-only` を活用し、「何が変わったか」の差分情報だけを観測せよ。

## 5. 出力フォーマットの高密度化

データの出力やパースを行う場合、無駄な空白や罫線を含むリッチなテキストテーブル出力などを避けよ。
*   JSONはインデントをつけずにフラットに出力させる、あるいはCSVやMarkdownテーブルなど、LLMにとってトークン効率の高い形式を強制すること。

## 6. データフレーム（表データ）の極限圧縮
PolarsやPandasのデータを観測する際、生データをそのままコンテキストに出力することを全面禁止する。
*   必ず `df.glimpse()` (Polars) や `df.schema`、あるいは `df.head(3)` と `df.tail(3)` などのメソッドを利用し、「メタデータ（型と構造）＋最小限のサンプル」だけに圧縮して出力せよ。

## 7. セマンティック・ディフ（意味論的差分）の導入
変更内容を確認する際、トークンを消費する生のコード行全体ではなく「何が変わったか」だけを抽出する。
*   `git diff -U0` (コンテキスト行ゼロ) を利用するか、ファイルの骨組みベースでの構造的な変更点だけを抽出して観測せよ。

## 8. プログレッシブ・ディスクロージャー（段階的開示）の徹底
必要性が証明されるまで詳細データを引き出さないという「段階的な探索プロセス」を徹底せよ。
*   第1段階: ファイル名やディレクトリ構造のみを把握する
*   第2段階: ファイルの行数と関数名・クラス名などのシグネチャだけを把握する（検索ツール）
*   第3段階: 対象の行（数行〜数十行）だけをピンポイントで把握する（部分読み込み）
*   **閾値による分岐**: 段階的開示にも往復コストがある。**目安300行以下の小ファイルは一発で全体を読んでよい**（3往復するより合計トークンが安い）。300行超のファイルにのみ第1〜第3段階を適用する。

## 9. サブエージェント委譲（最大の圧縮手段）
広域探索（「どこで X を使っているか全部調べる」「この機能の実装箇所を洗い出す」等）は、メイン文脈で出力をいくら削っても積み上がる。
*   探索・調査系タスクはサブエージェントに委譲し、**結論（ファイルパス・要約・判定）だけ**をメイン文脈に受け取る。中間の検索結果やファイル内容はサブエージェント側で消費させる。
*   1サブエージェント1タスク。曖昧な丸投げではなく「何を返すか」を指定して投げる。

## 10. 構造化出力の射影（Projection）
人間向けのリッチな出力をパースするのではなく、最初から機械可読形式で必要フィールドだけを取り出す。
*   **CLI**: `gh pr list --json number,title -q '.[]'` のように `--json` + クエリで射影する。汎用JSONは `jq -c '.items[] | {id, status}'` で必要キーのみ・フラット出力。
*   **SQL/DuckDB**: `SELECT *` 禁止。必要列のみ + `LIMIT`。行ダンプの代わりに `COUNT(*)` や集計で答えられないか先に検討する。

## 11. 数値基準（デフォルトの上限）
定性的な判断に頼らず、以下を既定値とする。
*   単一ツール出力は**原則100行以内**を目標とする。100行超が予想されるコマンド（ビルド・テストスイート・長時間処理）は、出力を一時ファイルへリダイレクトし、検索ツール・末尾抽出で必要部分だけ取り出す。
*   `git diff` はまず `--stat` で全体像を見てから、ファイル単位で個別に差分を見る。
*   ディレクトリ把握は再帰一覧を撒き散らさず、深さを絞るかファイル名パターンで限定する。

## 12. アンチパターン即時変換表
左を打ちそうになったら、必ず右に変換する。

| アンチパターン | 代替 |
|---|---|
| `cat <大ファイル>` / 全行読み込み | 構造把握 → 部分読み込み（§3, §8） |
| `ls -R` / 再帰フル一覧 | パターン指定のファイル検索、深さ制限 |
| `npm install`（素のまま） | `npm install --quiet --no-progress` |
| `pip list` / `npm ls` 全件 | 対象パッケージ名で grep |
| `git log`（引数なし） | `git log --oneline -n 5` |
| `git diff`（いきなり全体） | `git diff --stat` → ファイル単位 |
| verbose な docker build ログ全文 | リダイレクト → 失敗時のみ末尾・エラー周辺を抽出 |
| DataFrame の `print(df)` | `df.glimpse()` / schema + head/tail（§6） |
| 曖昧語での広いWeb検索を何度も撃つ | 固有名詞・年・単位まで絞った1発クエリ（§13） |
| ヒットしたURL全部をFetch | 一次資料と疑われる1〜2件に絞ってFetch（§13） |
| WebFetchでページ全文をそのまま受ける | `prompt` で射影し必要事実だけ抽出（§13） |
| 広範なリサーチをメイン文脈で自分で回す | サブエージェントに委譲し結論だけ受け取る（§9, §13） |

## 13. Web検索・Web取得の圧縮（WebSearch / WebFetch）
検索エンジン自体が要約済みスニペットを返すため生ログ問題は小さいが、往復回数とFetch量は自分で制御する必要がある。
*   **クエリは一発で絞る**: 曖昧・広いクエリで何度も撃ち直すのではなく、固有名詞・年・単位まで含めて1クエリで当てにいく（例: `"Roquette LG Chem 2001 acquisition sorbitol"`）。再検索は新情報が要る時だけ。
*   **Fetchは選別してから**: 検索結果を眺めて一次資料らしい1〜2件だけをFetchする。ヒットしたURLを全件Fetchしない。
*   **WebFetchは`prompt`で射影**: ページ全文をコンテキストに流し込まず、`prompt`引数で「知りたい事実（数値・日付・主体）だけ抽出して」と指定し、要約結果だけを受け取る。
*   **広域調査はサブエージェント委譲**（§9再掲・最重要）: 「競合各社の資本構成を横断的に調べる」のような複数ページにまたがる調査はサブエージェントへ投げ、メイン文脈には結論（事実・出典・確度タグ）だけを受け取る。中間の検索結果・ページ本文はサブエージェント側で消費させる。
*   **確度タグは維持**: 圧縮してもソースの追跡可能性は落とさない。[一次]/[要検証]等のタグと出典URLは要約後も必ず残す（圧縮は情報量を削るためのものであり、検証可能性を犠牲にしない）。

**【絶対掟】**
常に自問せよ：「このコマンド/ツールの出力はすべて必要か？ノイズを削ぎ落とすフラグや事前フィルタリングは見落としていないか？」

**【安全弁 — 圧縮しすぎの禁止】**
圧縮は**成功パスの最適化**であり、失敗の証拠を落とすためのものではない。
*   exit code と失敗のシグナルは絶対に観測から落とさない。
*   コマンドが失敗したら、次の1回はフィルタを緩めて（末尾行数を増やす・エラー周辺の context を広げる・フルログをファイルで保全する）再観測してよい。原因特定より圧縮を優先してはならない。
*   末尾抽出で root cause（最初に出た例外・コンパイルエラーの1行目）が窓の外に落ちている疑いがあれば、ログ先頭側も検索すること。
