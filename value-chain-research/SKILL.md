# Value Chain Research

## Overview

業界を問わず「バリューチェーン／サプライチェーンの構造」を体系調査し、Obsidian Vaultに一次資料ベースで書き残すための汎用ワークフロー。化粧品業界SCM調査（`D:\Vault\cosme`）で確立した型を抽象化したもの。

**核心原則**:
1. 一次資料（企業公式IR、ベンダー公式プレスリリース、査読論文）でしか主張を確定しない。二次資料（業界メディア、SI企業ブログ）しかない場合は確度タグを下げる。
2. 結果には確度タグと出典URLを必ず添える。「たぶんこうだろう」は⚠️要検証タグ付きで書く。
3. Vault本体には要点とタグだけを書き、詳細な検証経緯・根拠URLの一覧は別ファイル（CHANGELOG）に集約する。
4. 解決済みの完了報告（「〜を訂正した」「〜が確認できた」）は本文中の警告ブロックに残さない。今も未解決の制約だけを警告として残す。

## When to Use

- 特定業界（化粧品、食品、自動車部品、アパレル等）のSCM・バリューチェーン構造を新規に調べる
- 既存の業界調査Vaultに「調査の観点として足りないものはあるか」と聞かれた
- 企業のIT導入事実（ERP/S&OP/WMS/MES）を横並び比較したい
- 業界に関する学術論文・ケーススタディをサーベイしたい
- 既存の調査資料群にファクトチェックをかけたい、または重複コンテンツを統廃合したい

**使わない場面**: 単発で1社の一般的な会社概要を知りたいだけ（WebSearch/WebFetchで十分）。財務分析・株価分析が主目的（このスキルは組織構造・プロセス・ITアーキテクチャに焦点）。

## 調査観点チェックリスト（5＋1軸）

業界を問わず、以下の軸で観点の抜け漏れを確認する。ユーザーに「観点は足りているか」と聞かれたら、まずこの一覧と照らし合わせて欠けている軸を指摘する。

1. **組織ガバナンス**: ブランド/事業部門 vs SCM/Operations部門の役割分担・RACI・力学。中央集権型（Control Tower）か分散型（メゾン自律等）か。
2. **プロセス・実務運用**: S&OP/IBPサイクル、新商品ローンチの逆算計画（レトロプランニング）、商品改廃（EOL）・過剰在庫（SLOB）処理。
3. **企業別ケーススタディ＋ITシステム**: 主要プレイヤーの組織図・ITスタック（ERP/S&OP/WMS/MES/調達）横並び比較。技術アーキテクチャ視点（データフロー）と組織視点（誰が何を使うか）は別ファイルに分けてよいが、データ自体は重複させない。
4. **学術論文・ケーススタディサーベイ**: 業界固有の査読論文、HBS/WEF等のケースレポート。書誌情報は個別にWebFetchで直接検証する（検索エンジンの要約だけを信用しない）。
5. **地域組織とグローバル本社の権限分界**: 本社・地域統括・各国法人の間でどこまで意思決定権限が委譲されているか。見落とされがちな軸なので明示的に確認する。
6. **（業界固有の追加軸）**: 規制対応（例：化粧品ならEU PPWR、食品なら賞味期限規制）、ESG・サステナビリティ施策の実在性確認、財務指標（CCC/DSI等）とSCM施策の接続。

## How to Run

### フェーズ1: スコープ確認
ユーザーに対象業界・対象企業リストを確認する。「主要N社」を決め打ちせず、業界の構造（グローバルメガプレイヤー / リージョナルプレイヤー等）に応じて自然な区切りを相談する。

### フェーズ2: 一次調査
`web-search`スキル（`gemini_websearch.py` / `gemini_webfetch.py`）で各観点を調査する。企業のIT導入事実は特に誇張されやすいので、以下の確度基準で格付けする：

| タグ | 基準 |
| :--- | :--- |
| ✅✅ | 企業名を明示した一次〜準一次資料（ベンダー公式プレスリリース、企業公式IR）で確認 |
| ✅ | 業界メディア・ベンダーブログ等の二次資料で概ね確認 |
| ⚠️ | 具体的ベンダー名の一次確認ができず、独自の抽象化表現や業界標準からの推測の疑いがある |
| 未検証 | 探索したが確認できなかった、または深追いしなかった |

`vertexaisearch.cloud.google.com`のようなリダイレクトURLは、解決失敗（`(解決失敗、リダイレクトURLのまま)`表記）のまま一次資料として採用しない。

論文サーベイでは、検索エンジンの要約を鵜呑みにせず、DOI経由で書誌情報（著者・巻号・発行年・雑誌 or 会議プロシーディングス）を個別にWebFetchで直接確認する。「著者名が実在するか」は特に捏造されやすいポイント。

### フェーズ3: Vault構造化
以下のファイル分割を出発点として使う（1業界9〜10社規模を想定。対象社数に応じて調整）:

```
00_MASTER_INDEX.md              全体ナレッジマップ（ファイル一覧・Mermaid俯瞰図のみ、詳細内容は複製しない）
MASTER_xxx_Report.md            統合白書（各章は要約＋番号ファイルへの参照リンク中心。詳細表は複製しない）
01_Governance_and_Organization/ 組織・ブランドvsSCM役割・RACI
02_Process_and_Operations/      S&OP・NPD・SLOB・ESG規制等のプロセス別ファイル
03_Company_Studies_and_IT/      企業別ケーススタディ＋IT比較表
04_Academic_Papers_and_Translations/  論文サーベイ総覧＋個別和訳ノート
CHANGELOG_FactCheck.md          検証結果・訂正履歴・根拠URLの一元管理
```

**重複を作らない原則**: 同じ表（9社IT比較表など）を2箇所に書きたくなったら、どちらかを「要約＋参照リンク」にする。詳細を持つ側は「切り口が違う」ファイル（組織構造視点 vs 技術アーキテクチャ視点）に限定し、単純な全体最適化用の複製は作らない。

### フェーズ4: CAUTION運用
各ファイル冒頭の`[!CAUTION]`ブロックには**今も未解決の制約**だけを書く。

- 良い例: 「⚠️ 資生堂DataRobot予測精度等の具体的数値は出所未検証」
- 悪い例: 「ファクトチェック実施済み。旧版で誤っていた著者名は訂正済み」（完了報告はCAUTIONに書かない。訂正した経緯はCHANGELOGへ）

判断基準: 過去形（〜が判明した／〜を訂正した／〜が確認できた）で書かれた文はCAUTIONから除去する。現在形（〜は未検証／〜が確認できていない）で書かれた文は残す。ただし「単一の実在論文ではなく合成資料と判定した」のように、判定結果自体が本文の扱い方を左右する重要な警告は、経緯を含めて残してよい。

確度の凡例（✅✅/✅/⚠️の意味説明）はCAUTIONではなく`[!NOTE]`が適切。「警告」ではなく「読み方の説明」だから。

### フェーズ5: CHANGELOG記録
`CHANGELOG_FactCheck.md`に日付見出しで追記していく。各エントリに含めるもの:
- 背景（なぜこの調査をしたか）
- 検証結果の表（主張／検証結果／出典URL）
- 検証方法（使ったツール・手法）

過去のエントリは削除・書き換えしない（監査ログとして時系列に積み上げる）。ただし各レポートファイル側のCAUTIONは最新状態に保つ（フェーズ4）。

## Key Practices (learned the hard way)

- **同じ表を複数ファイルに複製すると、後で確度検証結果を1箇所にしか反映し忘れる**。Grepで横断検索し「同一データが何箇所にあるか」を先に把握してから反映作業に入る。
- **「一次資料・ベンダー事例発表裏付け済み」のような自己宣言的な見出しは疑ってかかる**。実態を確認すると大半が未検証、というケースが頻発する。
- **サステナビリティ施策名は特に誤記・混同が起きやすい**（例:「KIREI Innovation」という実在しない名称と実際の「Kirei Lifestyle Plan」の混同）。公式サイトで正式名称を確認する。
- **学術論文の著者名は捏造・誤記のリスクが高い**。AIが生成した合成資料を「実在論文の和訳」として扱ってしまうミスが起きやすいので、著者名・DOI・掲載誌は個別に裏取りする。
- **Mermaid図を大量に含める場合は`mermaid-cli`（`mmdc`）で機械的にレンダリング検証する**。目視だけでは、サブグラフタイトルの丸括弧やアポストロフィが原因のパースエラーを見逃す。
- **「深追いしない」と決めた項目は、要検証タグを付けたまま残してよい**。全項目を裏取りしようとすると調査が終わらない。CHANGELOGに「出所不明のまま残る主要な数値」として一覧化しておけば十分。

## Common Mistakes

| 症状 | 原因 | 対処 |
|---|---|---|
| IT確度検証をしたのに一部ファイルだけ反映漏れ | 同じ9社IT比較表が3〜4ファイルに複製されていた | 反映前にGrepで同一データの複製箇所を全部洗い出す |
| CAUTIONブロックが年々肥大化する | 解決済みの完了報告を消さずに積み上げている | 過去形の文はCAUTIONから除去しCHANGELOGに移す（フェーズ4参照） |
| 業界メディアの記事をそのまま一次資料として引用 | SI企業の事例紹介・ベンダーブログを企業公式発表と混同 | ドメインが企業/ベンダー公式かを確認し、確度タグを分ける |
| 学術論文の和訳ノートが実は存在しない論文だった | 検索AIの要約を鵜呑みにし、著者名・書誌情報を未検証のまま和訳作成 | DOI/掲載誌名を個別WebFetchで直接確認してから和訳に着手する |
